внутренняя валюта **GRAM**. Ведётся по полному мастер-промпту (разделы 1–11).
Дата старта: 2026-10-26.
Состояние: TIER 0–2 закрыты; TIER 3 (3.1–3.5) закрыт; TIER 4 (4.1–4.10) закрыт (dual betting,
краш, история ставок, Апгрейд, Крафт, Плинко, Дайс, Мины, Спины; сим-тесты RTP через реальные сервисы);
TIER 5 закрыт (PVP HUB, Solo Jackpot, TVT: Ice vs Fire, синхронизация раундов, история, лидерборд);
TIER 6 закрыт (рейтинг, задания, билеты, розыгрыш, рефералка);
**TIER 7 ПОЛНОСТЬЮ ЗАКРЫТ (7.1–7.9):**
- 7.1: PostgreSQL 16 + FastAPI + async SQLAlchemy 2 + Alembic + Pydantic 2 + docker-compose + /health
- 7.2: Пользователи и авторизация Telegram WebApp initData (HMAC-SHA256, токены HS256, рефералы)
- 7.3: Баланс и журнал транзакций (row-level locking, защита от овердрафта, дедупликация)
- 7.4: Инвентарь и каталог (19 подарков по конфигурации продукта, начисление, атомарная продажа)
- 7.5: API кейсов (20 платных + 2 бесплатных, серверные кулдауны UTC, CSPRNG-розыгрыш по весам EV-солвера)
- 7.6: API игровых сессий (Дайс, Мины, серверный ролл/раскладка, автозабор, реальный лидерборд)
- 7.7: Идемпотентность и конкурентные запросы (asyncio.gather тесты на предотвращение овердрафта и lost update)
- 7.8: WebSocket и Server-Sent Events (SSE стриминг Live Drops + WebSocket для Ракетки)
- 7.9: Сквозной E2E интеграционный тест платформы (40/40 тестов backend зелёные).

`vite build` ✓, Docker live health / API ✓.
Рабочее правило: после каждого подпункта — пересборка и выкат в бота (см. «Активный запуск»).
Ритм циклов (по запросу пользователя): по ЧЕТЫРЕ шага за цикл.

Правило приоритета: любые массивы коэффициентов (кейсы, Dice, Mines, Plinko, Upgrade, Craft, Spins, PVP)
обязаны быть связаны с реальным распределением вероятностей. Выплаты не подбираются визуально —
для каждого исхода рассчитывается математическое ожидание и проверяется, что EV (RTP) совпадает
с настроенным `RTP_factor`.

Зафиксированные отклонения от стека спеки (по правилу 2.1 «не менять стек без необходимости»):
стили — CSS Modules вместо Tailwind (аналог уже в проекте); анимации — CSS keyframes вместо
Framer Motion (переоценить при сложных игровых анимациях TIER 4); иконки — inline SVG вместо
Lucide. Деньги — целые минорные единицы (1 GRAM = 100 minor) вместо NUMERIC-строк на клиенте;
NUMERIC обязателен в БД (TIER 7).

## Игровая математика — обязательные правила (спецификация 10.7–10.16)

### 10.7. Dice

Поля: множитель, больше/меньше, шанс выигрыша, ползунок. Изменение любого поля пересчитывает остальные.

Формула отображения: `multiplier = RTP_factor / win_probability`.
Начальный `RTP_factor = 0.98`, значение вынесено в конфигурацию игры.

Документированные границы и правила (обязательны к реализации и к этому документу):

- Границы шанса: `win_probability ∈ [0.01, 0.98]` (1%–98%). Ниже 1% и выше 98% ползунок не допускает.
- Исход розыгрыша: целое число `roll ∈ [0, 9999]` (10 000 равновероятных значений), генерируется сервером (CSPRNG).
- Ставка «больше X»: `p = (9999 - X) / 10000`; ставка «меньше X»: `p = X / 10000` (X — целое от 1 до 9999).
- Округление множителя: только вниз (floor) до 4 знаков — гарантия, что округление никогда не поднимает RTP выше 0.98.
- Выплата: `floor(bet_minor · multiplier)` в минорных единицах; дробные единицы игроку не начисляются.
- Вероятности исходов: ровно два исхода — выигрыш с `p` и проигрыш с `1 - p`;
  `EV = (RTP - 1) · bet` (house edge 2%) при любом положении ползунка.
- Точность: все расчёты в целых числах / decimal; плавающая точка не используется для денег.
- При изменении `RTP_factor` конфигом пересчёт EV обязателен; UI показывает активное значение.

### 10.8. Mines

- Сетка 5×5 (25 клеток), мин настраивается от 1 до 24.
- Мины фиксируются на сервере в момент старта раунда; раскладка не покидает сервер.
  Клиенту запрещено отправлять содержимое нераскрытых клеток, если это позволяет заранее определить результат.
- Вероятность выживания после `k` безопасных открытий:
  `P(k) = C(25 - m, k) / C(25, k)`, где `m` — число мин.
- Множитель на шаге `k`: `mult(k) = floor2(RTP_mines / P(k))` — округление вниз до 2 знаков.
  Полный сбор (`k = 25 - m`): `mult = floor2(RTP_mines · C(25, m))`.
- Коэффициенты по шагам генерируются формулой, а не массивом «руками»; массив в конфиге допустим
  только как кэш формулы и проверяется тестом на совпадение с формулой.
- EV каждого шага: `P(k) · mult(k) ≤ RTP_mines` (округление вниз — в пользу казны). Тест 4.10 проверяет это для всех пар `(m, k)`.
- Cashout: сервер проверяет легитимность шагов и выполняет атомарное обновление баланса и инвентаря.
- Проигрыш: ставка сгорает, фиксируется в истории; атомарность та же.

### 10.9. Spins

- Поле 5×5; подарки и специальные символы; ставка; скорость анимации; автоспин; покупка бонуса; двойной шанс.
- Распределение символов задаётся весами на сервере; таблица выплат связана с вероятностями:
  EV спина = Σ p_i · payout_i · bet = RTP_spins · bet. Любая правка весов требует пересчёта EV и цены бонуса.
- Автоспин: ограниченная последовательность отдельных серверных запросов (например, серии по 10/25/50/100),
  а не бесконечный клиентский цикл; каждый спин валидируется и списывается сервером отдельно.
- Покупка бонуса: цена = `EV(бонусного спина) / RTP_purchase`; рассчитывается сервером, клиент только отображает.
- Специальные множители и «двойной шанс»: применяются только серверной логикой; клиент получает готовый результат.
- Скорость анимации — косметический параметр клиента, на исход не влияет.

### 10.10. Free Cases

- Типы: FREE 24 (кулдаун 24 часа) и FREE (1 час — конфигурация продукта).
- Право получения, кулдауны и лимиты проверяет исключительно backend по серверному времени (UTC).
- Смена времени на устройстве / клиентские манипуляции не позволяют обойти ограничения:
  все таймеры считаются от `now()` БД/сервера, клиентское время игнорируется.
- Выдача бесплатного кейса использует то же распределение и тот же расчёт EV, что и платный аналог
  (содержимое FREE/FREE 24 решено EV-солвером с целевым EV 0.5 / 5 GRAM при RTP 0.98 — проверено тестом).

### 10.11. Crash («Ракетка») — математика Demo-движка (4.2)

- Точка краша: `crash = max(1, floor2(RTP / (1 − u)))`, `u ~ U[0, 1)`, `RTP = 0.98`.
- Следствие: `P(crash ≥ m) = RTP / m` — для x2 это 0.49, для x10 — 0.098
  (подтверждено симуляцией 100 000 раундов, тест `demoCrashService.test.ts`).
- Множитель растёт экспоненциально: ×2 каждые 4 секунды, дискретно по тикам 50мс
  (`GROWTH_PER_TICK = 2^(TICK_MS/4000)`).
- Кешаут на отображаемом множителе m (сетка 0.01): выигрыш = `floor(ставка × m)`
  (`mulByMultiplier`, округление вниз — в пользу казны).
- EV ставки с кешаутом на m: `P(crash > m) · m = RTP · m / (m + 0.01) ≤ RTP` —
  дискретность сетки работает в пользу казны (правило проекта); симуляция EV — 4.10.
- Граница «x1.00»: при u ≤ 0.02 краш мгновенный — ставка сгорает сразу (P = 2%).
- В production эта формула исполняется сервером с CSPRNG + Provably Fair (4.3/TIER 7);
  клиентский движок — только Demo Mode, честно помечен на экране.

### 10.12. Plinko — математика и КОРРЕКЦИЯ формулы дорожной карты (4.6)

- Шар проходит n «монеток» (влево/вправо), карманов n+1; `P(k) = C(n, k) / 2^n`.
- ВАЖНО (исправлено в этом цикле): буквальная формула дорожной карты `m_k = RTP / P(k)`
  даёт EV ряда = Σ P(k)·m_k = (n+1)·RTP — экономика сломана. Верное нормирование:
  `m_k = floor2( RTP / (P(k) · (n+1)) )` — тогда Σ P(k)·m_k = RTP ровно до округления,
  а округление вниз (floor2) смещает EV чуть ниже RTP — в пользу казны (правило проекта).
- Целочисленная реализация (RTP = 0.98 → RTP_PCT = 98):
  `m_k = floor(98 · 2^n / (C(n,k) · (n+1))) / 100` — никакого float до финального /100.
- Точный RTP ряда — рационал `numerator / (2^n · 100)` (BigInt, `plinkoExactRtp`);
  тест утверждает окно **[0.97, 0.98] для каждого ряда** n ∈ {8, 12, 16}.
- Максимумы (крайние карманы): n=8 → **x27.87**, n=12 → **x308.77**, n=16 → **x3777.95**.
- Выплата: `floor(ставка × m_k)` (mulByMultiplier — округление вниз, в пользу казны);
  исход (путь шара) определяется ДО анимации — анимация только визуализирует.
- Ряды фиксированы конфигом: 8/12/16 (не произвольные). В production бросок исполняется
  сервером с CSPRNG (TIER 7, 7.6); клиентский движок — Demo Mode, помечен на экране.
- Симуляция ≥100k раундов — 4.10.

### 10.13. Upgrade и Craft — математика (4.4/4.5)

- Апгрейд: `p = min(1, (s / t) · RTP)`; EV в стоимости = p·t ≤ 0.98·s всегда.
  Показ процента — целочисленный `floor(9800·s/t)/100` (float-ловушка 489.99… обойдена,
  `upgradeChancePercent`).
- Крафт: кандидаты `v_i > 0.98·S` (целочисленное сравнение v·100 > 98·S), максимум 8
  по возрастанию; `p_i = 0.98·S / v_i`; цель равномерно; **EV = (1/|C|)·Σ p_i·v_i = 0.98·S
  точно** (без округлений — тождество проверено тестом для 4 значений S). Проигрыш
  сжигает входные предметы; выигрыш — один целевой предмет.
- В production расчёт и бросок обеих игр исполняются сервером (TIER 7, 7.6).

### 10.14. Dice — реализация (4.7)

- Спека 10.7 реализована буквально: roll ∈ [0, 9999] (floor(u·10⁴), 10 000 равновероятных
  значений); «больше X»: p = (9999−X)/10⁴, «меньше X»: p = X/10⁴.
- Границы шанса [0.01, 0.98] из спеки → допустимые цели: over X ∈ [199, 9899]
  (c = 9999−X), under X ∈ [100, 9800] (c = X); clampDiceTarget зажимает ползунок/инпуты.
- Множитель — ТОЛЬКО формула: m4 = floor(98·10⁶/c) (floor до 4 знаков, целочисленно).
  Гарантия p·m ≤ 0.98: floor не может поднять — тест полного перебора обоих направлений.
- Примеры: p=0.49 → x2.00 ровно; c=5099 → m4 = 19219 → x1.9219 (не 1.9212 — floor).
- Пересчёт полей (спека «изменение любого поля пересчитывает остальные»): цель из
  множителя c = floor(98·10⁶/m4) с зажимом [100, 9800] (diceTargetFromMultiplier);
  chance→target: c = round(pct·100); направление меняет только интерпретацию цели.
- Выплата floor(bet·m4/10⁴); отображение множителя/шанса — trим нулей после toFixed
  (`.replace(/\.?0+$/, '')` — безопасно ТОЛЬКО после toFixed: у строки всегда есть точка).
- Ролл делает demo-сервис (rng-хук для тестов); production — сервер с CSPRNG (7.6).

### 10.15. Mines — реализация (4.8)

- Спека 10.8 реализована буквально: mult_hundredths = floor(98·C(25,k)/C(25−m,k)) —
  гипергеометрия с округлением вниз до сотых; полный сбор k = 25−m покрыт той же формулой
  (C(25−m,25−m) = 1 → floor(98·C(25,m)); тест согласованности для всех m ∈ [1, 24]).

### 10.16. Spins — реализация (4.9) и сим-тесты (4.10)

- Колесо: 10 символов — 9 подарков каталога (plush-pepe … chill-flame, веса
  1,2,3,5,7,9,12,15,18) + бонус-символ (вес 8; «двойной шанс» → 16). W = 80 или 88.
- Нормализация — та же КОРРЕКЦИЯ, что в Плинко (10.12): m_i = floor(98·W/(w_i·10))/100
  ⇒ p_i·m_i = честная доля RTP/10 на каждый символ ⇒ EV ≤ RTP при любом W.
  Значения (обычный): x7.84/x3.92/x2.61/x1.56/x1.12/x0.87/x0.65/x0.52/x0.43.
- Бонус-символ: сам НЕ платит (иначе EV двойного счёта) — даёт один бесплатный спин

- Свободная ставка бонус-спина: floor(bet·W/(10·w_b)) — обычный = bet (вклад бонуса в EV

- Экран: сетка 5×5 — витрина; ячейка победителя подсвечивается, НО исход решает

### Общие серверные инварианты

- Все розыгрыши — на сервере (CSPRNG / Provably Fair по решению 7.x); клиент только отображает.
- Любое изменение баланса/инвентаря — одна атомарная транзакция БД с записью в журнал транзакций.
- Один запрос ставки несёт уникальный `client_request_id`; повтор не создаёт повторную ставку
  и не начисляет выигрыш дважды (контракт отрепетирован в `demoCaseService`).
- Конфиг игры (`RTP_factor` для каждой игры) — единый источник правды; значения по умолчанию 0.98,
  изменение конфига требует прогона тестов математики (4.10).
- Точность денег: на клиенте — целые минорные единицы; в БД — NUMERIC/Decimal;
  округление всегда вниз в пользу казны, кроме случаев, явно описанных в спецификации.
